# 秒传生成/导入 频控与体验优化方案（参考 123FastLink v1.2.x）

状态：**六步已全部实施完毕（脚本版本升到 1.3.12），待维护者本地实测**。按项目铁律，实测通过前不 commit、不打 tag。范围：仅 `油猴脚本/123-helper/123-helper.user.js` + `tests/`（客户端后端本期未动）。文末「六、实施结果与偏差」记录了落地时的差异。

## 〇、已定决策（2026-09-15 维护者确认）

1. **频控取向：自适应门控**——不做保守固定限速，也不在设置里暴露双模式；起步尽量快，撞限全局冷却降速，恢复后逐步提速。
2. **接口线路：改成 auto 探测**——`fastLane` 开关升级为 `fastlinkTools.apiRoute: auto | mirror | canonical | page`，默认 `auto`，任务开始前小样本探测三条线路，运行中撞限自动换道并提示。
3. **建目录的请求放大器：一页 500 + 父目录 name→id 索引缓存**，并实测「直接 createFolder、靠 `duplicate:1` 拿已存在 ID」能否成立；成立则存在性检查整体下线，只在返回缺 ID 时回落列举。
4. **本期范围：全做**——频控层 + 削减请求 + 线路 auto + 导入语义（未命中不算失败、暂停）+ 运行明细（当前路径/大小/速率/ETA/冷却倒计时）+ 版本更新内容弹窗。

## 一、为什么我们的会"请求过于频繁"，他的不会

对比两份脚本的实际请求行为（行号为本仓库脚本）：

| 维度 | 123-helper（我们） | 123FastLink（参考） | 后果 |
| --- | --- | --- | --- |
| 目录列举并发 | `collectFastlinkFiles` L7503/7556：按层 `mapLimit` 8 个目录同时扫（导入侧预建目录 L6948 用 12，reuse 用 24/32） | 全程串行递归，目录树一个请求一个请求地走 | 我们瞬间 QPS 高数倍，直接顶到 `file/list/new` 的 ~15 QPS/用户频控 |
| 请求间距 | 无任何 pacing：`listAll` L1091-1099 翻页之间零延时；reuse 路径无门控（`shareApiGate` L147 只挂在分享列举 L1107） | `PROACTIVE_DELAY_MS=50`（L543）主动间隔，加网络往返实际 ~5-10 QPS | 参考脚本天然待在配额内 |
| 撞限后行为 | 每个 worker 各自 6 次退避（L980 `800*1.7^n`，封顶 6s），退避结束又同时打回去 | 限流错误按条目重试 5s；**连续 3 次限流 → 全局暂停 8s**（L816-822），所有请求一起停 | 我们的重试风暴把同一个频控窗口继续灌满，6 次烧完就抛错，用户看到"频繁"并中断（只给部分抢救 L22079） |
| 每层列举的请求数 | `limit=100` 且 `listAll` 翻到 `Next=-1` 为止；更糟的是 `findChildFolder` L1533 用 **`listAll(父目录)` 全量翻页**判断子目录是否存在 | `listDirectoryContents(parent, 500)` 一次 500 条（L1564、L1477），不递归翻完 | 一个大目录（几千条目）下建 1 层子目录，我们要 30-50 个请求，他 1 个 → 导入时请求量差一到两个数量级 |
| 接口域名 | 默认 `location.origin`（L944/952，页面域名 `*.123pan.cn`），fastLane 默认关（L2237）；实测"32 并发 85 次/秒不限流"是在 `www.123865.com` 上做的 | 也是 `window.location.host`（同源），但因为串行+间隔，压根不触发 | 页面域名前面是 CDN/WAF（分享接口 60 次/分钟那套同源证据），按 IP+窗口计数，最容易报"频繁" |

一句话根因：**我们把并发当成吞吐手段，但服务端按"请求速率"限流；既没有全局节流门，也没有全局熔断，还额外制造了大量可避免的列举请求（全量翻页 + 建目录前的存在性检查）。**

参考脚本值得抄的不是"串行"本身，而是这三点：① 主动间距；② 撞限后**全局**冷却（AIMD 的乘性减）；③ 少发请求（limit 500、存在性检查不翻全量）。参考脚本的短板也很明显：串行在千万级条目下要跑数天、没有断点续传、没有流式解析、没有 base62 之外的格式治理——这些正是我们已经建好的能力，必须保留。

## 二、方案总纲：保留流式/断点骨架，把"并发即速度"改成"门控即速度"

### 1. 统一频控层（核心，最小侵入）

把 `shareApiGate`（L147-229，含 `waitTurn`/`hit`/`ok`/`configureFor`/`snapshot`/`restore`）抽成通用工厂 `createApiGate(profile)`，实例化三条车道：

- `gate.list` — `/b/api/file/list/new`（导出扫描、预建目录、存在性检查共用），起步 12 req/s（间距 ~80ms），撞限直接乘性减到 2 req/s 并全局冷却。
- `gate.write` — `/b/api/file/upload_request`（秒传 reuse / createFolder / 上传种子文件），起步按当前线路实测（默认域名 32 并发 85 req/s 的水位 → 间距 0，封顶 80 req/s）。
- `gate.share` — 现 `shareApiGate`，行为不变，只做参数化。

接入点：`Pan123Api.request()` L974 增加 `pacing` 选项，在真正 `fetch` 前 `await pacing.waitTurn(signal, onWait)`；成功后 `pacing.ok()`，识别为频控时 `pacing.hit()`。车道按 host 配置（页面域名 / 123865 / api.123278 三套档位，`configureFor(host)` 已有先例）。

**全局熔断优先于条目重试**：任一请求 `hit()` 后，车道进入冷却，`waitTurn` 让所有 worker 一起等；条目级 `attempts` 不再"各自烧 6 次"，而是"等门开"。这样并发数只影响内存与流水深度，不再影响瞬时 QPS——这是能同时拿到"不报频繁"和"千万级跑得完"的关键。

`share-gate-jitter.test.mjs` / `share-pacing.test.mjs` 现成的用例可以直接改造成通用门测试，回归成本可控。

### 2. 削减请求数（收益比调并发大一个数量级）

- `listPage` L1063 的 `limit` 默认 100 → **500**（参考脚本实测可用），并做一次上限探测（500/1000 各拉一页，取服务端不报错的最大值，落 kv 记住）。导出扫描与 `listAll` 直接少 5 倍请求。
- `findChildFolder` L1525 不再 `listAll` 全量翻页：改为「**单页 500 + 必要时游标续页**」，且缓存父目录子项索引（`listingCache` 已有，扩成 `parent → Map(name→id)`，导入任务生命周期内复用）。
- 更进一步（需实测）：建目录前**不做存在性检查**，直接 `createFolder`（`duplicate:1` 语义下服务端返回已存在目录 ID），只有返回缺 ID 时才回落列举。这一条能把"预建目录"请求数压到 O(新目录数)。
- 导出扫描：断点续扫时剔除陈旧记录（L7559-7567）是 `files.filter` 全表扫描，十万级目录会有平方级开销 → 用 `Map(prefix → count)` 或按目录 ID 记账替代（顺手）。

### 3. 线路/域名策略：从"开关"升级为"三档 + 自动"

`fastLane`（L2237）改 `fastlinkTools.apiRoute`: `auto | mirror(api.123278) | canonical(www.123865) | page(当前页域名)`，默认 `auto`：

- 秒传任务开始时用一次「线路探测」（复用 L19384 已有的"测试当前目录 API"雏形，扩成小样本压测：各 host 拉 5-10 个请求，看是否出现 100011/频繁/403，按结果选车道 + 写入档位）。
- 运行中撞限 3 次且冷却翻倍仍复现 → 会话内换线路（沿用 `markLaneDead` L965 的会话级健康位），并明确提示"已切换到 X 线路"。
- 现有两段式回退（L996-1028）与 `credentials:"omit"` 规则、分享同源请求要 include 的坑保持不动。

维护者此前实测「api.123278 16~24 线程 ≈150 次/秒」，说明镜像域名频控口径确实比页面域名宽松——`auto` 的目标就是每次自动落在最宽松的那条道上，而不是让用户靠勾选项猜。

### 4. 导入执行层：分组并发 + 暂停 + 失败语义

- `createFastlinkStreamImporter.consume`（L7254）与数组路径（L6916）保留 `mapLimit` 骨架与批次 8192、`ensurePath` promise 缓存、doneSet（L7070）、断点 v3（L7050-7051，每 2s 落盘）——**流式与断点这套千万级能力一条都不动**。
- worker 数与"速度"解耦后，`writeConcurrency` 语义改为"流水深度"（默认 16，上限 64），实际速率由 `gate.write` 决定；设置页文案同步改写，避免继续误导"越高越快"。
- 新增**暂停**（现在只有停止 L21504）：`pauseController`，worker 在取下一条前 `await gate.pauseGate.wait()`；参考脚本 L1517 的 100ms 轮询可以做得更干净（promise 信号）。
- 断点里持久化门控状态（`snapshot`/`restore`，L179-189 已有），续跑不带着刚触发的限流状态立刻再撞。
- 区分三类结果：秒传成功 / 云端无同哈希可复用（**正常未命中，不算失败**，可选"未命中清单"导出）/ 真失败（网络、频控耗尽）。当前 `reuseFile` L1350 抛错进 `failDetails`，会把 1400 万条里未命中的一大片染成"失败"，统计失真。

### 5. 明细与进度（抄参考脚本的体验，做得更强）

参考脚本的观感来自：`📁 扫描文件夹: 路径`、`✔️ 文件: 路径 (大小)`、当前文件 + `extraStatus`、成功/失败计数、全局暂停提示。我们现在的进度条（L19238、`setProgress` L21510）只有 message + done/total + 停止按钮。

新增 `createRunLedger`（内存环形 200 行 + 可选全量落盘）：

- 扫描期：当前目录路径、已扫目录数、已收文件数、累计体积、速率（文件/秒）、ETA、`扫描文件夹: X` / `文件: X (1.2 GB)` 明细行。
- 导入期：当前条目路径 + 大小 + etag 前 8 位、状态徽标（成功/未命中/跳过/清理/失败）、速率、冷却倒计时（"频控冷却中，X 秒后自动继续"）。
- 渲染仍走 100ms 节流；日志窗口可折叠，展开即明细表格（复用 `resultTable` L19326 的分页样式）。
- 结果页保留 `invalid/sanitized/invalidReasons/invalidSamples`（L7309-7324）并加"按状态筛选 + 复制/下载完整明细 CSV"。

注意千万级场景内存：明细只进环形缓冲（封顶 200 行）+ 分片落盘，绝不整表驻留（AGENTS.md 里 2-3GB 内存的坑就是这么踩出来的）。

### 6. 更新内容通知

- 新增 `changelog` 常量表（版本 → 要点数组），头部 `@version` 变化即弹一次：`GM_getValue("Cloud123.Helper.SeenVersion")` 比对，确认后写回；样式照参考脚本"我已知晓"那种单按钮模态，接进我们现有 modal 体系。
- 油猴菜单常驻「查看更新内容」，随时可回看全量 changelog。
- 不做"联网检查新版"（Tampermonkey 自己会查 `@updateURL`，脚本内再拉一次徒增请求）。

### 7. 格式互通校验（顺手补强）

我们已支持 `123FSLinkV1/V2$`、`123FLCPV1/V2$`、base62 etag（L5998-6001、L6303-6318）。补一项：导入流式路径（L6378 scanner）在 JSON **未声明** `usesBase62EtagsInExport` 时，按 etag 形态推断（32 位纯 hex = 原始，否则 base62），与参考脚本 L1398 的启发式一致；推断结果在结果页明示（避免"未命中"被误读为文件不存在）。

## 四、验收（本地实测口径）

- 小样：选一个 3-5 千条目、含多层目录的文件夹，导出 → 全程不得出现"频繁/100011 中断"（允许日志里出现"冷却 Xs 后继续"然后自动恢复）。
- 中样：同一份 JSON 反向导入到新目录，对比改动前后的请求总数（面板显示）与耗时；期望请求数下降 ≥50%，零人工重试。
- 大样：手上有几 G / 千万级 JSON 时，先按现有分档跑 5 万条小样验证未命中率与门控水位，再决定是否全量（全量前保留断点，可分晚跑）。
- 互通：用参考脚本导出的 JSON 导入我们能吃；我们导出的它能吃（V2 + commonPath + base62）。
- 断点：中途关页再开，进度与门控状态都能续接；不重复转存（doneSet 指纹生效）。

## 五、保留与不采纳清单

保留（我们独有、参考脚本没有）：>8MB 流式解析与背压（L6681、L7813）、断点 v3 + doneSet 位压缩、无效条目清理与分类计数、二级秒传种子、拆分/转换工具、分享直连 123865 + 分车道限速、影库/客户端联动接口。

不采纳：全程严格串行（千万级跑不完）、无断点、每次条目都打日志到 DOM（十万级会卡死页面）、`getFolderDetail` 逐目录额外请求、脚本内自行联网查更新。

## 六、实施结果与偏差（2026-09-15 落地）

全部六步已实现，与方案的差异如下（都是实施中发现方案本身不够严谨而做的修正）：

1. **限速门的排队机制从「比较 lastStart」改成「预约时隙」**。方案照抄了旧 `shareApiGate` 的写法，但 `gate-pacing` 第一次跑就暴露：N 个请求在同一瞬间进入时都算出 `gap<0`，会**一起放行**，等于只约束「波与波」之间、不约束同波内并发——正是原来 8 个 worker 能打满 15 QPS 配额的机制。现在 `nextFree` 管同波内排队、`lastStart + interval` 管顺序请求的最小间距，两条旧测试（`share-pacing` / `share-gate-jitter`）继续通过。
2. **「等门开」预算从 60 次收到「3 次 + 累计 20 秒」双闸，且超预算打 `paceExhausted` 终局**。方案里「等门开不烧重试预算」如果无上限，会让一个被硬封的账号把千万级任务冻在第一个文件上（第一次实现直接把 `list-100011-retry` 用例挂到 45 分钟级等待）。语义改为：门负责全局冷却（其他条目自然排队），单条按失败记账继续跑，断点保证下次续传。
3. **签名与请求超时计时挪到紧贴 fetch、每线路尝试独立 AbortController**。加了门之后，等待发生在 fetch 之前，若按原结构会在等待前算签名、并在等待期间跑 30s 超时计时——跨分钟签名失效与「冷却被误判成网络故障」两个老坑会同时踩到。
4. **未命中分桶顺带修了一个断点安全性问题**：数组路径原来「只要没有失败就清断点」，现在**有未命中也不清**（未命中条目没写 done 指纹，清档会让下次重跑把已成功条目再转一遍，`duplicate:1` 下生成一堆「名字 (1)」副本）。
5. **探测排序加了固定偏置 tie-break**（mirror > canonical > page）：三条线路延迟差距在毫秒噪声内时不该来回抖动。
6. **设置页的「秒传接口线路」下拉与「立即测速选路」按钮已按维护者 2026-09-16 的指示删除**：线路完全交给自动探测（任务开始前一次、结果缓存 30 分钟、运行中撞限自动换道），不再提供手动档位。保留内部状态 `fastlinkTools.routePreference`（`auto|mirror`，`mirror` 只作为旧 `fastLane` 开关的兼容位），以及「秒传设置 → 恢复默认」这个清偏好 + 作废探测缓存的出口。
7. 其余按方案落地：每页 500（探测到异常自动降回 100）、`listAll` 重复页止损、`findChildFolder` 名索引 + 新建覆盖表、`apiRoute` 四档 + 自动换道 + 「立即测速选路」、`panRunControl` 暂停、`createRunLedger` 明细与摘要、结果页筛选 + CSV、`SCRIPT_CHANGELOG` 更新通知与菜单入口。

新增回归测试（`tests/`）：`gate-pacing`、`request-gate`、`drive-route`、`fastlink-import-miss`、`run-ledger`、`changelog-notice`；`fastlink-secondary` 补了 `// src/api.js` 切片，`fastlink-fastlane` 在用例内先把网盘门间距调零（它验的是域名与重试语义，不该被排队干扰）。另有开发用 `tests/rt.sh`（macOS 无 `timeout` 命令，带超时跑单个测试）。

**下一步（维护者实测）**：选 3-5 千条目、多层目录的文件夹跑导出 → 反向导入到新目录，看进度条明细与「未命中」统计、确认不再出现「请求过于频繁」中断；有几十 G / 千万级 JSON 时先用「拆分」切小样验秒传命中率与门的水位，再决定全量。
